# Pre-registration: "Does a Coding Agent Know When It's Out of Date?"

Status: **FROZEN 10 Nov 2026** (revised after the pilots, before any main run). Frozen version = the git commit whose SHA-256 manifest
(`prereg/manifest.json`, built by `tools/make_prereg.py`) is posted publicly **before** the main runs.
Anything decided after the main runs start is reported as exploratory.

## 0. What the pilots showed (before this registration; reported in the paper)
C0 (no tools) on Modal: post-cutoff tasks with an example in the issue 24/24 resolved; silent changes with
an example 8/8; silent changes whose spec is only in the repo (README/docstring) 7/8; silent changes with
**no spec anywhere** 4/8 (click 0/2, Float64 0/2, groupby 2/2, sklearn 2/2 with 13–26 tool calls). Kaggle vs
Modal C0: 21/22 tasks same outcome. So the study is built around **specification availability**.

## 1. Questions
- **RQ1 (knowing vs fixing):** does missing knowledge of a library change stop the agent, depending on how
  much of the expected behaviour is written down (L1 example in the issue, L2 spec in the repo only, L3 no
  spec anywhere)?
- **RQ2 (self-awareness):** when web search or local docs are available but optional, does the agent use
  them, and before or only after a failure? Does an explicit staleness hint change that (C2 vs C1)?
- **RQ3 (do tools help where knowledge is needed?):** on L3, do C1/C3/C4 raise the resolve rate over C0;
  are offline docs (C3) as good as web search (C1)?
- **RQ4 (cost / harm):** on L1/L2 and control tasks, do the tools raise cost (tool calls, tokens, time) or
  lower success?
(The earlier 4-bit vs full-precision question was dropped on 8 Nov: no Gemma 4 endpoint; covered elsewhere.)

## 2. Model, serving, sampling (identical in every condition)
- Gemma 4 31B IT QAT w4a16 (`gemma-4-31b-it-qat-w4a16-ct`), Kaggle model V2; on Modal the same 8 files
  (sha256-identical, incl. Kaggle's chat template).
- vLLM 0.19.1 started by the official notebook code (`adk_submission.VllmServer`, same `VllmConfig`).
- Official sampling (`sample_submission/configs/sampling.yaml`): temperature 0.2, top_p 0.95,
  max_output_tokens 16384, thinking budget 4096 (include_thoughts). No seed (runs are stochastic).
- Harness: official swegemma 0.2.11 / adk-submission 0.2.13 / adk-eval-core 0.1.0, subprocess sandbox.

## 3. Tasks
- **Post-cutoff (12):** our tasks, each a library change released after the Jan 2025 cutoff that the model
  answered wrongly in the knowledge probe (2 rounds, hand-labelled). Old library version passes the hidden
  test, new version fails, reference fix passes (validated 12/12 on PyPI, offline, and in the official
  grader). Frozen file: `tasks_postcutoff/out/tasks.jsonl`.
- **Silent changes (4 changes, 3 issue variants):** pandas 3.0 groupby(observed=False) unobserved groups,
  scikit-learn 1.8 weighted median_absolute_error, click 8.2+ flag envvar, pandas 3.0 Float64 NaN→NA. Code
  for the old version runs without error or warning on the new version but gives a different result.
  Variants: informative (example values in the issue), vague (no example; README/docstring define the
  behaviour), no-spec (defining text removed; only the old library "knew" the behaviour). Same hidden test
  and reference fix in every variant; each validated (old passes, new fails, fix passes) at the exact pins.
  Files: `tasks_silent/out*/`. All tasks and issue texts are synthetic (written by us), modelled on the
  style of real upgrade reports.
- **Main-run task groups** (`configs/main_tasks.json`, assigned by design before any main run):
  **L1** = 12 post-cutoff + 4 silent informative (16); **L2** = 3 silent vague (sklearn's vague variant is
  identical to its no-spec variant and is dropped); **L3** = 4 silent no-spec; **control** = the 10
  calibration control tasks (user decision 10 Nov, budget). 33 tasks.
- **Control (30 sampled, 10 used):** sampled from the public dev set (gold fix passes, empty patch fails,
  near-duplicates merged; seed 2026). Frozen files: `configs/control_tasks.json`, `configs/calibration_tasks.json`.
- **Pre-specified subgroups** (labelled 9 Nov, before any condition run, from the issue text only):
  - post-cutoff **hinted** = the issue or its error message names the API element involved in the change
    (parameter, attribute, key or command): marshmallow_validates ('data_key'), marshmallow_context
    ('context'), click_command_suffix ("Did you mean 'init'?"), django_checkconstraint ('check'),
    networkx_node_link ('links'), pandas_tz_zone ('zone'), starlette_lifespan ('on_startup');
    **not hinted** (symptom only): polars_streaming, click_no_args_exit, sklearn_adaboost,
    sklearn_logreg_multiclass, pandas_epoch_seconds.
  - control **pre-cutoff fix** (merged before Feb 2025; 10 Rich tasks) vs **post-cutoff fix** (20).

## 4. Conditions (generated by `harness/build_conditions.py` from the official sample agent)
Common to all: LoRA adapters removed (base model), graph tools and their prompt mentions removed, budget
900 s / 60 tool calls / 15 min, one scratch-file rule (`/tmp`). Exact prompt additions are in the code.
| ID | Adds | Prompt addition |
|---|---|---|
| C0 | nothing | - |
| C1 | `web-search` skill (Tavily via a local relay; query ≤ 200 chars, ≤ 8 results) | "A web-search skill is available … Using it is optional." |
| C2 | as C1 | C1 text + staleness hint ("libraries … may be newer than your training data …") |
| C3 | `library-docs` skill (offline: installed version, API, signatures, docstrings, source) | "A library-docs skill is available … Using it is optional." |
| C4 | both skills | both notes |

## 5. Platforms
**All main conditions (C0–C4) run on Modal** (decided 10 Nov, before any main run), so every comparison
is within one platform. Modal is required for C1/C2/C4 anyway (internet; Kaggle L4 sessions must have
internet disabled). The Modal environment is a replica of the Kaggle GPU notebook proven equivalent:
`pip freeze` 969 = 969, grading 84/84 identical, snapshots 30/30, model files 8/8 (incl. Kaggle's chat
template). Hardware: Modal L40S, tp=1 (Kaggle: 4× L4, tp=4; Modal had no L4×4 capacity).
**Transfer check (pilot, excluded from the main analysis):** C0 on 22 tasks (`configs/calibration_tasks.json`)
× 2 repeats on both Kaggle and Modal, reported as evidence that Modal results carry over to the official
Kaggle environment: cross-platform disagreement in per-task outcome compared with within-platform repeat
disagreement, plus the share of runs at the 15-minute cap on each platform.

## 6. Repeats
R = **2** runs per task × condition (33 tasks × 5 conditions × 2 = 330 runs). Fixed 10 Nov from the
budget (Modal credit); calibration showed 1 of 10 control tasks flipping between repeats.

## 7. Outcomes
- **Primary:** resolve rate on **L3** per condition; contrasts C1−C0, C3−C0, C4−C0, C2−C1, C3−C1.
- **Specification gradient:** C0 resolve rate and cost across L1 → L2 → L3.
- **Cost (L1, L2):** tool calls, tokens, wall time per run, and number of repo edits (trial and error),
  per condition; does a tool turn repeated guessing into a look-up?
- **Harm:** resolve rate and cost on control tasks, C1/C3/C4 − C0.
- **Behaviour (from traces):** share of runs with ≥ 1 search / docs call; first search/docs call before vs
  after the first failing test run; number of calls; on control tasks: unnecessary use.
- **Cost:** tool calls, LLM calls, prompt/completion tokens, wall time; per run and per solved task.
- **Failure taxonomy** (manual, on unresolved post-cutoff runs; labels: old API kept, wrong-version docs,
  result ignored, tool-call error, budget exhausted, other), labelled blind to condition where possible.

## 8. Analysis
Unit = task (outcome = share of its R runs resolved), paired across conditions. Report rates with 95%
bootstrap CIs (10,000 task-level resamples, seed 2026) and paired permutation tests on the per-task
differences (exact or 10,000 permutations). With 12 post-cutoff tasks the study is small: results are
presented as effect sizes with intervals, not as significance claims; no multiple-comparison claims.
Subgroups (hinted / not hinted; pre/post-cutoff control) are descriptive.
Excluded runs: only harness failures (no agent output because of an infrastructure error), re-run once and
reported.
